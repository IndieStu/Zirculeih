# ADR-023: Non-blocking requests and atomic local weekly series

Date: 2026-10-17. Status: Implements accepted ADR-003/008 under the
[Phase-8 owner authorization](../OWNER_APPROVAL_PHASE_8.md).

## Decision

Keep confirmed Booking/AllocationClaim and physical Loan invariants unchanged.
ReservationRequest is a non-blocking proposal for one or more RequestOccurrences;
each occurrence has a permanent original local key, and gains an original root
Booking only at approval. Bundle component bookings retain their existing group.
No nullable fictitious unit, custody, provisional claim or hidden capacity hold.
Requests explicitly say “Angefragt – noch nicht reserviert”. Resource policies
choose auto/manual confirmation; existing policies default to auto. All weekly
requests require explicit approval, even when single bookings auto-confirm.

Weekly expansion accepts selected weekdays and exactly one of count/until. Count
means occurrences, not weeks. The configured resource cap starts at 52; the
smallest selected component cap wins. A separate execution guard permits at most
366 occurrences and a 3660-day expansion horizon. Current booking/grant horizons
still constrain every actual booking. Local dates/wall times are expanded before
UTC conversion. Ambiguous/nonexistent local times never silently move: pending
occurrence adjustments explicitly resolve an offset, change the local time or
omit that date. Physical appointments expand in local wall time independently;
unresolved DST appointments cannot pass approval.

Request headers, selected resource membership and original occurrences retain
immutable identity; additive RequestAdjustment evidence stores pending edits.
Approval refuses a changed bundle member set or time mode/timezone rather than
silently changing the request. Current policies, requirements, groups, qualification
evidence, agreement versions, asset state, selected pools and all occupancy rules
are checked again. The original applicant is preserved on the proposal; binding
Bookings record the actual approving actor and beneficiary.

The existing authorization-write transaction/lock serializes request decisions
with allocation, policy/membership changes, suspensions and blocks. A bounded
uncommitted simulation invokes the actual allocator, including all selected bundle
members and previous occurrences in that simulation. It rolls back bookings,
claims, receipts and audit writes, then reports every occurrence without disclosing
other borrowers. Approval simulates then repeats allocation in the same protected
transaction; either all eligible occurrences commit or none. Simulation never
persists a hold. Approval requires scoped booking.approve plus the ordinary own/
for-others create rights and current beneficiary eligibility, across every member.
Employee and protected system-admin flags confer no operational rights. Queue and
staff detail require booking.read_all across the original request scope.

After approval, one occurrence can be cancelled or moved atomically via the same
allocator. Original Booking identity is not overwritten: cancel it, create a
replacement and append an immutable OccurrenceException chain. Original local key
and previous decisions remain readable. Moving requires scoped approval and normal
create/manage rights; cancellation uses existing own/manage and deadline rules.
A conflicting move restores the original through transaction rollback. Bundles
stay atomic. Whole-series cancellation processes the remaining nonterminal
occurrences together, retaining past completed/cancelled history. Active physical
custody cannot be cancelled or replaced to evade return rules.

PostgreSQL triggers retain request/occurrence/exception history and enforce full
occurrence counts, unique original positions, original booking linkage, terminal
request transitions and complete approved occurrence linkage at commit.

## Limits and consequences

This is a bounded weekly planner, not an arbitrary RRULE engine. “This and all
following” editing/splitting is deferred; change individual exceptions or cancel
remaining occurrences and create a new bounded proposal. No hidden partial
approval. Requests with all dates omitted cannot be approved. No Phase-9 email,
ICS feeds, new runtime dependency, production or NCtest deployment is introduced.
The global authorization lock is an existing throughput limit; simulations are
explicit POST operations, rate limited, and capped.

Acceptance: AC-10/11/23 plus permission, DST, physical agreement, pool/bundle,
SQL-history, idempotence and PostgreSQL concurrency tests in tests/test_phase8.py.
