# ADR-024: Transactional notifications and private calendar subscriptions

Date: 18.10.2026. Status: Implementation under [owner authorization](../OWNER_APPROVAL_PHASE_9.md).
Extends accepted ADR-015; [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545) is the
calendar contract. No change to booking, allocation, room/machine or loan boundaries.

## Delivery

The existing service-authored immutable audit event is the explicit allowlisted
notification source. The same domain transaction writes Delivery, uniquely keyed
by event identity; rollback removes both. Incidents and due reminders have stable
idempotency keys. There are no model signals, SMTP calls in booking transactions,
Redis/Celery services, inferred physical returns or startup jobs. Account token
messages enter the same outbox before commit; their existing on-commit immediate
attempt remains available and failure leaves a retriable encrypted message.

Render a plain-text snapshot with bounded templates, explicit de/en locale and only
`${url}` / `${when}` variables. Subject is a fixed line without template variables
or CR/LF. Auth links, recipient and body are encrypted using existing reviewed
cryptography/Fernet with a domain-separated key derived from the server signing
secret. Keep this secret in stopped-write backups; retained SECRET_KEY_FALLBACKS
allow controlled key rotation. No plaintext links, SMTP responses or credentials
in status logs. Only explicit system.configure can change templates/settings or
retry failures. Its queue view exposes message UUID/type/status, not borrower
names, contacts or message contents. Optional qualification mail respects both
organization enablement and personal preference; necessary transaction messages
cannot be disabled by that preference.

Workers claim rows under row locks with two-minute UUID leases, maximum configured
attempts (initially 5, editable 1–10), exponential bounded retry delays and stable
outbox identity. Before SMTP, current account/recipient and object authorization
are checked under the shared authorization lock. SMTP timeout remains five seconds.
This intentionally shares the initial throughput limit. No concurrent worker sends
the same live lease. Native SMTP cannot guarantee exactly-once delivery across a
crash after server acceptance and before recording success. Delivery is at-least-once;
standard queued messages carry stable Message-ID, but clients need not deduplicate.
Idempotent enqueue/worker controls are not a claim that all mail servers deduplicate.
“Übergeben” means backend accepted, not read or guaranteed inbox delivery.

Explicit schedule_reminders and deliver_notifications commands run through an
operator scheduler. Current appointments/custody decide pickup/return/overdue;
expected return or reservation end never closes possession. Keys include due-time
revision/repetition bucket. Obsolete reminders are skipped after return, extension,
expiry or superseding overdue bucket. Bundle children and series confirmations are
suppressed in favor of the root/approval summary. Single pending occurrences stay
explicitly non-binding in the receipt. Newly published agreements remain gates;
no mail can accept a contract for someone else.

Terminal payloads can be removed by explicit purge_notification_payloads --days N;
30 days is an operational command default, not a legal retention claim. Idempotency
keys/status survive; failed messages without content cannot be retried. Review mode
retains the existing file mail backend and never sends to the Internet.

## Calendars

Use a bounded personal/operational month view and the existing central booking
projection, with scoped Resource/Category/Location/Organization filters. The accepted
resource month/day availability selection remains unchanged. An application calendar
is a read view, not checkout evidence or a new allocation engine.

A CalendarFeed has active verified owner, explicit immutable scope, expiry (editable
1–366 days; default 90), opaque 256-bit token stored only as SHA-256 and permanent
revocation history. Raw link is displayed once after creation/regeneration, never
stored in sessions. Regeneration invalidates the old URL immediately. Current owner,
object scopes and resource visibility are checked on every fetch; deny before any
old cached payload. No shared content cache or conditional 304 serves stale rights.
All feed responses are private/no-store/no-referrer; application logs contain route
patterns rather than token paths. Operator/proxy access logs must also omit the
private URL. Already downloaded client data cannot be remotely erased.

Scopes grant no rights beyond current owner: personal = own currently visible
bookings; operational = booking.read_all and currently visible resources, with
per-resource explicit denies. No borrower name/contact, internal asset/location,
consent text or employee metadata is exported. Event content is authored public
resource title and location label, approved period and mapped CONFIRMED/CANCELLED
status. There is no anonymous or permanent organization masterfeed.

Each logical occurrence exports a stable UUID-based UID independent of host/title.
Serien are expanded first-class events rather than an unbounded RRULE. Replacement
chains collapse to their original occurrence identity; cancelled occurrences retain
the same UID. CalendarRevision stores a fingerprint and monotonic sequence/modified
instant when the public event projection changes. This small read-side publication
state does not mutate Booking/Loan. UTC Z times represent instants; day reservations
use DATE and exclusive end dates. Text escaping, UTF-8-safe 75-octet folding and CRLF
are implemented in a narrow serializer and independently parsed with a test-only
icalendar dependency. No runtime calendar package or external API is introduced.

Feeds cover rolling 90 days past / 366 days future, fail explicitly beyond 5000
visible events, and have bounded owner management and request rates. Month views
request one month window before scoped projection. No silent truncation, generic
API, CalDAV or reverse synchronization.

## Acceptance

Concurrency/retry/privacy/SQL-state, ICS parser, UID update/cancel, DATE/DST, expiry,
rotation and permission loss tests accompany the implementation. The owner explicitly
declines a Nextcloud test instance and will perform CAL-06 manually later. Record it
as pending; no automatic cloud provisioning or claim of real Nextcloud interoperability.
Phase 10 and any production/NCtest deployment remain separate gates.
