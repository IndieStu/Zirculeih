# ADR-025: Inventory snapshots and staffed asset operations

18.10.2026. Implementation under [Phase-10 authorization](../OWNER_APPROVAL_PHASE_10.md).
Extends ADR-011; asset/resource/booking/loan remain separate.

Inventory runs have immutable organization/location/category scope. Start materializes
active unarchived assets, expected location/category/name/revision and custody state.
A scoped actor must have run action plus asset.read for every included asset; deny
in a subtree fails the start rather than silently changing the declared scope.
Maximum 2000 expected assets per run; use narrower scopes above that bound.
Read revalidates current asset access including unexpected observations, before
counts/pagination/export. Reports are internal, never public or borrower profiles.

Observation uses the existing read-only identifier resolver and a separate explicit
record command. Request UUID prevents duplicate writes; aliases canonicalize to one
asset. Different genuine observations can record multiple locations without double
counting. No location/lifecycle/loan writes follow a scan. Unexpected authorized
assets do not silently expand the expectation snapshot. Unknown codes are not stored.

All mutations take existing AuthorizationRevision lock before run/task/asset rows.
This is the same lock used by moves, checkout, return and booking allocation. Start,
observation, completion and custody/move operations therefore have a documented
serial boundary. PostgreSQL run-row guards also serialize observations against
closing. Completion stores a frozen minimal assessment with cutoff, seen/not-seen,
wrong-location/unexpected and open/overdue custody references. Not seen never means
lost; later moves or returns cannot rewrite the completed report.

Discrepancy decisions remain separate audited records after closing. A move decision
requires asset.move at source and destination, current revision and explicit reason,
and uses the existing inventory service. Temporary finding / later clarification
never changes master location. No automatic lost/disposal action.

Maintenance records use planned → in_progress → completed/cancelled with audited
revision checks. Beginning work changes linked asset lifecycle via existing asset
service, blocking physical units and flagging existing promises. Completion requires
explicit condition/release decision and never clears another open work order or
independent resource block. Recurring inspections create a new planned follow-up
at completion with bounded day interval; no phantom telemetry or auto-completed work.
Attachments reuse existing private AssetMedia authorization/storage.

Bulk move/condition operations are explicit bounded previews carrying IDs/revisions,
then atomic service calls with per-object revalidation; no quiet partial success.
Reports aggregate current inventory, loan/custody, booking volume/reserved duration
and maintenance, scoped independently by current grants. Reserved duration is not
actual machine operating time or a capacity-normalized utilization percentage.

Staffed terminal uses normal staff session and explicit workflow selection, local
transient FIFO/request IDs, no global keyboard hook, no browser persistent PII.
Inventory scanning can record observations; lending links use existing confirmation
services and never commit on scan. Inactivity locks/reset via server session generation;
stale terminal requests fail. Explicit logout and no-store prevent previous-person
content reuse. No self-service device trust, camera dependency or offline commit.
Real HID hardware acceptance remains a documented owner/pilot check, not simulated
hardware success. QR generation is local, dependency-reviewed, labels contain only
an opaque existing asset identifier, never an access token or private metadata.
