# ADR-015: Betriebsdashboard, Integrationsgrenzen und lebendes Handbuch

Datum: 15.10.2026 · Status: Owner-Anforderung verbindlich, Umsetzung/Plan zur Phase-3-Abnahme.

## Kontext

[Originalergänzung](../OWNER_ADDITION_DASHBOARD_API_HANDBOOK.md). Das Dashboard organisiert konkrete Arbeit; API und Kalender teilen Domainservices; Handbuch ist fortlaufendes Lieferergebnis. Bestehende ADRs bleiben gültig, einschließlich unbefristeter Einweisungen ohne individuellen Entzug im Initialbetrieb. Das illustrative spätere Beispiel „auslaufende Qualifikation“ schafft keinen Ablaufmechanismus entgegen OD-07; vorerst nur fehlende Einweisungen/Accountprobleme als spätere Hinweise.

## Dashboard

Serverseitige Projektion produktiver Domänen. Phase 3 zeigt berechtigte Assets mit Schadens-/Prüfbedarf oder eingeschränktem Lebenszyklus, inaktive sichtbare Standorte, vorhandene Schnellaktionen und nachgeordnete Bestandszahlen. Kein universeller Organisationsdatenzugriff, keine Fakebookings/Loans/Inventurläufe, keine Platzhaltercharts und keine toten Zukunftsbuttons. Ohne Betriebsrechte persönlicher Kontobereich. Systemadministration bekommt keine impliziten operativen Datensichten.

Gemeinsame zentrale Batch-Grantprüfung für Inventarlisten, gleiche Algebra wie Einzelprüfung; nur frischer Requestbestand, keine Autorisierungscaches über Writes. Scopefilter vor Pagination/Counts. Spätere Phasen ergänzen ausdrücklich passende Projektionen: Phase 5 Ressourcennutzung/Heute, Phase 6 Abholung/Rückgabe/überfällige Loans und gefährdete Folgereservierungen, Phase 7 Wartung/Einweisungsprobleme, Phase 8 Genehmigungen, Phase 10 Inventurdifferenzen. Timeline kombiniert Raum-/Maschinen-/Fahrzeug-/Ausleihvorgänge, nicht nur Dinge.

## API und Kalender

[Integrationsvertrag](../INTEGRATIONS.md) beschreibt Versionierung `/api/v1/`, aktuelle Owner-/Clientrechte als Tokenobergrenze, keine Klartext-Masterkeys, Pagination/Filter/Fehler/Zeit/Rate Limits und OpenAPI-Gate. Produktive API gemäß akzeptiertem Plan ab Phase 11; jetzt keine vorgezogenen Fakeendpunkte oder neue DRF-Abhängigkeit. Opaque Scope-IDs sind keine Autorisierung. Controller/Serializer transportieren gemeinsame Serviceprojekte statt interne Modelle freizugeben.

ICS ab Phase 9 nach produktiver Bookingdomäne. Stable UID, RFC-5545, DST-/Datumssemantik, datenminimierte Scopefeeds und widerrufbare private Credential-URLs. Nextcloud Calendar ist Interoperabilitätsziel, kein proprietärer Runtimezwang. CalDAV/bidirektionale Synchronisation bleiben getrennte spätere Nutzen-/Komplexitätsentscheidung.

## Dokumentation und Definition of Done

[Handbuch](../handbook/README.md) unterscheidet normale Nutzer, Betriebspersonal, Organisations- und Systemadministration. Aufgabenanleitungen für reale Phase-2/3-Oberflächen, keine spekulativen Zukunftskapitel. Entwickler-/API-/Architektur- und Betriebsdokumente bleiben getrennte Zielgruppen. Screenshots mit synthetischen Daten an aussagekräftigen Stellen, nicht für jeden trivialen Zustand.

Ab jetzt ist eine Nutzer-/Adminfunktion erst vollständig, wenn Implementierung, sinnvolle automatische Tests, Autorisierungs-/Sicherheitsprüfungen, relevante Handbuchkapitel sowie bei API bzw. Architekturänderung entsprechende Vertrags-/ADR-Dokumente aktualisiert sind. CI prüft Handbuchstruktur/Links und neue Akzeptanzabdeckung; sachliche Vollständigkeit bleibt Teil der menschlichen Feature-Review. Kein Metatest kann die redaktionelle Abnahme ersetzen.
