# ADR-020 – Owner correction pass: human interface and requirement gaps

2026-10-16. Authorized by OWNER_UX_CORRECTION.md, within the existing Phase-6
review branch. No general Phase 7 authorization and no bundle/recurrence work.

All six supplied screenshots were inspected: myTurn catalogue (10.13.19), room
detail (10.13.37), availability month (10.13.44), operational dashboard/sidebar
(10.13.57), Deelvo machine booking (10.20.31), physical booking (10.22.57).
Functional lessons: visible availability, selectable periods, grouped operational
navigation and concise controls. No visual copying or reference-image reuse.

Existing capabilities: resource categories are inventory Category M2M; category
CRUD/deactivation exists. ResourceType differs and needs an edit path. Detailed
locations stay internal; add an explicitly authored optional catalogue area for
public filtering, rather than automatically exposing inventory descendants.
Distinct equipment can use separate existing Resources with explicit public names
and descriptions, each linked to its own physical Unit/Asset. Identical drills
remain a pool. No domain collapse or new unit-selection architecture is needed.

Versioned additional agreements, immutable acceptance and resource assignments
already exist, but enforcement currently covers only physical loans. Extend that
same service to onsite use and present only current outstanding requirements in
booking/account/resource administration. General lending/insurance remains mandatory
for physical loans; no new unnecessary per-drill agreement is introduced.

Qualifications have only a fail-closed policy boolean and an existing action name,
no productive type, issuance or resource relationship. Smallest authorized groundwork:
reusable named types, explicit resource requirements, immutable staff issuance,
no expiry/revocation/self-certification. Organization-scoped qualification.issue
is required to create/issue reusable types, avoiding implicit cross-resource
privilege escalation. Booking and checkout recheck both requirement kinds under
the existing authorization transaction; no operational override bypass.

Existing schedules intersect resource/location windows, with explicit exceptions;
there is no organization/category owner. Extend those same records and intersection
semantics to organization/category owners. All applicable restrictions intersect;
category/location/organization closures cannot be reopened by a more specific
resource exception. Batch vacation dates expand boundedly into existing exceptions.
No second scheduling engine. Existing bookings retain explicit review incidents.

The account invitation workflow must preserve self-accepted privacy notice,
verified email and self-chosen password. It reuses hashed single-use ActionTokens;
admin may invite an unverified account but cannot activate/verify/choose its password.
The owner approved one visible Admin role. Compose protected authority with explicit
operational grants at operator bootstrap and in the fictional review upgrade.
The protected flag remains internal; it is not a blanket bypass of operational
denies or resource requirements. Existing group editors are never promoted.
Review admin and the historical recovery account use the same composed access;
the latter remains for recovery/history, not a second visible privilege tier.

Presentation: concise labels, contextual help, conditional DST disambiguation,
read-only anonymous occupancy without identities and bounded calendar windows.
Availability is current occupancy/schedule information; final booking always uses
the same transactional allocator and current beneficiary eligibility.

Deployment: additive migrations and explicit additive demo enhancement only.
Preserve existing users, passwords, bookings, media and team-entered data. No reset.
