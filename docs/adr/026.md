# ADR-026: Bounded API adapters and current authorization ceilings

18.10.2026, implementation under [Phase-11 authorization](../OWNER_APPROVAL_PHASE_11.md).
Extends ADR-015/024. Contract: [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)
and header [Bearer usage](https://www.rfc-editor.org/rfc/rfc6750.html).

Use Django JSON adapters, no generic ORM serializers or additional runtime package.
Explicit v1 capabilities: minimal catalog/inventory, code resolution, preview/commit
CSV import and authorized CSV export, availability, own booking confirmation/cancel,
booking read, existing-reservation checkout and actual selected-line return. Initial
API does not administer accounts/groups/agreements/qualifications, plan series,
create spontaneous loans or expose private financial/media/contact fields.
All these domains remain available through their accepted web services.

IntegrationClient has verified active registered owner, name, immutable capability
ceiling and organization/resource/category/location/asset scope. Creating/managing
one requires explicit organization integration.manage, which itself grants no domain
power. Maximum 20 active clients per owner. Secrets are per-token opaque 256-bit
values, SHA-256 only at rest, one-time display. Tokens are immutable, expire in
1–90 days (initial 30), at most 20 active per client; rotation revokes old first.
Token capability subset and read-only setting further reduce the client ceiling.
Removing owner rights, integration.manage, membership, verification or active state,
client retirement, token expiry/revocation all affect the next request.

The API holds the existing authorization lock through credential check, projection
and domain transaction. A context-local ceiling is intersected inside the existing
authorization resolver for all owner checks, including nested bundle/checkout
services; it never substitutes a fake user or overwrites group grants. Current
beneficiary rights remain independent for different beneficiaries. Existing own-
object/public catalog shortcuts additionally receive explicit API scope checks.
Scope trees are resolved from current domain context, not client-supplied ancestors.
No token grants protected system actions. An immutable client capability may become
usable after an intentional future owner grant; it can never exceed current rights.

Bearer header only, no session fallback/query token/cookies, no CORS expansion.
Browser management retains session/CSRF and local-password confirmation for issuance.
Schema is public metadata, API data is authenticated and private/no-store/no-referrer.
JSON body max 64 KiB, strict fields/types/duplicate-key rejection, stable explicit
DTOs, max 50 results/page, bounded filters; scope filtering precedes counts/pages.
Separate 15-minute quotas: reads 600/IP and 600/client, writes 120/IP and 120/client;
invalid authentication 60/IP. No forwarding-header trust. Standard machine error
codes/request ID, no SQL, exception, payload, token or foreign object details.

Existing domain idempotency uses UUID keys namespaced by client, preventing two
clients of one actor from sharing a booking/loan operation key accidentally. Moves
and cancellation use required strong If-Match revisions; imports use their existing
one-time preview identity. Response DTOs are read again under current rights even
on retry. Audit adds client/token UUIDs, never the secret. No cached successful
response can bypass a later deny or revocation.

Times: RFC3339 aware instants map to accepted local policy time with explicit fold;
day mode uses ISO dates with inclusive requested end and explicit exclusive returned
end. Existing PostgreSQL allocation, agreements, identity evidence, qualifications,
opening/pickup and actual custody remain authoritative. Public schemas/examples
contain only fictional IDs and no live tokens. No production activation or actual
Authentik/Nextcloud connectivity is claimed by synthetic tests.
