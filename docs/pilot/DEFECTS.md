# Fehler und Feedback im Pilot

Noch kein Pilotfeedback eingegangen; keine erfundenen Testresultate oder Defekte.
Für jeden reproduzierbaren Fehler eine Kopie der Vorlage in der vereinbarten
geschützten Ablage beziehungsweise ein bereinigtes Repositoryissue anlegen.
Keine automatischen Issues, Mails oder Nachrichten an Dritte.

| Feld | Eintrag |
| --- | --- |
| Kennung / Titel | Offen |
| Aufgabe / Build / Umgebung | PILOT-ID, Commit und Rollenbezeichnung, keine Loginadresse |
| Schritte | Kleinste nachvollziehbare Folge, Zeit/Zeitzone bei Kalenderproblemen |
| Erwartetes Ergebnis | Konkretes fachliches oder Bedienergebnis |
| Tatsächliches Ergebnis | Beobachtung, Fehlermeldung/Request-ID ohne Roh-URL/Token |
| Auswirkung | Integrität/Datenschutz/Sicherheit, blockierter Kernablauf oder Bedienproblem |
| Workaround | Bekannt und fachlich zulässig / keiner |
| Priorität / Zuständigkeit | Owner und bearbeitende Person entscheiden |
| Korrektur / Nachweis | Commit, relevanter Regressionstest und erneute Aufgabenprüfung |
| Status | Neu / reproduziert / in Arbeit / zur Nachprüfung / bestätigt behoben / bewusst zurückgestellt |

Datenleck, Doppelbelegung, fremder Checkout oder verlorene Rücknahmen sind
Pilotstopper. Betroffene Writes stoppen und an verantwortliche Person melden;
Originaldaten und Audit erhalten. Keine Datenreparatur durch Löschen von Claims,
Zustimmungen oder Loanlinien. Betriebsrücknahme/Restore ausdrücklich abstimmen.

Ein blockierter Kernablauf ohne tragfähigen Workaround verhindert die Freigabe
dieses Pilotscopes. Kleinere Bedienpunkte können mit Ownerentscheidung,
Zuständigkeit und Termin zurückgestellt werden. „Nicht reproduziert“ ist keine
bestandene Prüfung. Ein Retest bestätigt den bestimmten Korrekturbuild.
